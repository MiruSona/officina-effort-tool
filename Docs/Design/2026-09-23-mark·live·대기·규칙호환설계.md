# mark · live · 대기 · 규칙 호환 설계 (2026-09-23)

> 대상 : 게임 저장소 실사용 피드백 중 미룬 것(`mark`·`--live`·「대기」)과 오늘 온 피드백
> (`Docs/Todo/2026-09-23-scan이rules의sub줄을모름피드백.md`). **1판·2판은 2026-09-26 구현했다** (3판 「대기」는 아직).

## 결론

1. **규칙 호환이 먼저다 (1판, S).** `rules.txt` 를 읽을 때 **모르는 종류는 경고하고 건너뛴다.**
   멈추는 것은 `rules --check` 뿐이다. 자동으로 더하는 줄은 「없어도 기본값으로 도는 종류」만 더한다.
   뒤의 `mark`·대기가 새 종류를 더할 수 있으므로, 이 판이 먼저 모든 자리에 깔려야 한다.
2. **`effort mark start/stop/show` 를 만든다 (2판, M~L).** mark 는 **시각만 exe 시계로 찍는다.**
   「실제」 값은 exe 가 **그 판의 transcript 파일을 찾아 두 시각 사이 본줄 구간**으로 잰다.
   시간·길이를 받는 인자는 없다 — 「시간을 손으로 적어 넣는 길은 없다」는 그대로 선다.
3. **`show --live` 는 따로 안 만든다.** `mark stop`·`mark show` 가 도는 판의 파일을 바로 읽으므로 그게 live 다.
   서브에이전트는 자기 `promptId` 를 모르니 `show <id>` 꼴로는 어차피 못 부른다.
4. **「대기」는 분류가 아니라 표시(구간 속성)로 둔다 (3판, M).** 도구 한 번이 오래 걸린 틈을 「대기 N분」으로
   따로 보여 준다. 총계·표본의 뜻은 안 바꾼다.
5. **⑶ `estimate 코딩:M` 은 이미 고쳐졌다.** 지금 exe(35864f5)는 「모르는 분류 "코딩"」을 찍는다.
   피드백은 **옛 exe(0b13d53, 09-21 빌드) 문제**다. 코드 일감 없음 — 1판의 「다시 빌드하라」 안내가 같은 뿌리를 덮는다.

## 1. 규칙 호환 (⑴ · ⑵)

### 무슨 일이 났나

- 새 exe(09-23)가 공용 `~/.effort/rules.txt` 끝에 `sub	max	120` 을 **자동으로 더했다.**
- 게임 저장소의 옛 exe(09-21)는 `sub` 를 모른다. `ParseRules` 가 「모르는 종류」로 **바로 실패**하고
  `scan` 이 종료 1 로 멈췄다 (`internal/classify/rules.go` `applyRuleLine`).
- `~/.effort/` 는 **기계에 하나**라 exe 여러 판이 나눠 쓴다. 한쪽이 더한 줄이 다른 쪽을 깨는 구조다.

### 앞으로의 규칙 (여기서 정한다)

| # | 규칙 |
| --- | --- |
| R1 | **읽을 때 모르는 종류는 경고하고 그 줄만 건너뛴다.** 경고는 stderr 에 종류별 한 줄 : 「rules.txt 162번째 줄 : 이 exe 가 모르는 종류 "sub" — 건너뜁니다. 더 새 exe 가 더한 줄일 수 있습니다 (EffortTool 폴더에서 `.\build.ps1`)」 |
| R2 | **아는 종류 안의 모르는 이름**(분류·크기·도구 집합)도 같은 식으로 경고 + 건너뜀. 새 분류가 생기면 옛 exe 가 `seed	대기 …` 에서 멈추기 때문이다 |
| R3 | **칸이 모자라거나 숫자가 틀린 줄은 지금처럼 실패한다.** 아는 종류를 잘못 쓴 것은 사람 실수라 조용히 넘기면 안 된다 |
| R4 | **`rules --check` 는 엄격하다.** 모르는 종류·이름도 오류로 보고 종료 1. 사람이 고친 뒤 확인하는 명령이라서다 |
| R5 | **새 종류는 「줄이 없어도 기본값으로 똑같이 도는 것」만 만든다.** 옛 exe 가 건너뛰어도 뜻이 안 바뀌어야 한다 (`sub` 는 이미 이 꼴 — `newRules` 기본 120) |
| R6 | **있는 종류의 칸 뜻·칸 수는 안 바꾼다.** 칸을 늘려야 하면 **뒤에 붙이고 없어도 되게** 한다. 옛 exe 는 `f[:need]` 로 뒤 칸을 이미 무시한다 |
| R7 | **자동 추가 머리 주석에 더한 exe 판을 적는다.** `# --- 2026-09-23 자동으로 더한 기본값 (sub) · effort 35864f5 ---`. 옛 exe 의 R1 경고가 이 주석을 읽어 「35864f5 가 더한 줄」까지 말해 준다 |
| R8 | 뜻이 바뀌는 변경(R5·R6 을 못 지킴)은 **새 종류 이름**으로 낸다. 옛 이름을 다른 뜻으로 다시 쓰지 않는다 |

- 지문(sha256)은 파일 바이트 그대로라 경고·건너뜀과 상관없다. 옛·새 exe 가 같은 파일을 보면 같은 지문이다.
- 경고는 **scan 한 판에 한 번**, 종류별로 묶어 찍는다. `estimate`·`list` 같은 읽기 명령은 경고를 한 줄로 줄인다
  (표 앞에 섞이면 파이프가 더러워진다 — 09-21 리뷰의 `printMissingMarks` stderr 결정과 같은 이유).

### ⑵ scan 실패 안내

- scan 이 **규칙·캐시 때문에** 실패할 때(종료 1·3) 끝에 한 줄을 더 찍는다 :
  「이 exe 는 `35864f5 · 2026-09-23` 판입니다. 서브모듈을 당긴 뒤라면 EffortTool 폴더에서 `.\build.ps1` 로 다시 빌드하세요.」
- 판 글은 `--version` 과 같은 값을 쓴다 (`dev` 면 그대로 `dev`).
- 한계 : **이 안내는 앞으로의 exe 에만 있다.** 지금 게임 저장소에 있는 옛 exe 는 여전히 멈춘다 — 다시 빌드하는 수밖에 없다.

### 캐시 판 호환 (같은 뿌리라 1판에 넣는다)

- 지금은 캐시 판이 다르면 `Stale()` 로 **통째로 다시 만든다.** 옛 exe(판 4)가 새 exe(판 5)의 캐시를 보면
  판 4로 덮어쓰고, 새 exe 가 다시 판 5로 덮는 **핑퐁**이 난다. 아직 판 5는 없어 실물 문제는 아니다.
- 규칙 : **캐시 판이 내 판보다 크면 덮지 않고 종료 1** + 위 ⑵ 안내. 작으면 지금처럼 다시 만든다.
- 판 글을 숫자로 견주어야 하므로 `SchemaVersion` 을 정수로 읽는다 (지금 `"4"`).

## 2. `effort mark` (서브에이전트가 자기 판을 잰다)

### 막힌 까닭

- 도는 갈래는 `cost-state` 줄이 없어 `scan` 이 마지막 작업을 `cost-state없음` 으로 표본에서 뺀다.
- 서브에이전트의 일은 **부모의 한 `promptId` 안**에 들어가 있어 작업 단위로는 쪼갤 수 없다.
- 서브에이전트는 자기 `promptId`·`agentId` 를 모른다. 그래서 `show` 로 제 것을 못 찾는다.
- 그런데 **도는 갈래의 transcript 파일은 이미 디스크에 있고 줄이 실시간으로 붙는다.**
  이 설계를 쓰는 판에서 직접 확인했다 — 지금 도는 서브에이전트 파일에 **지금 실행 중인 명령의 tool_use 줄이 이미 들어 있었다.**
- 같은 세션 `subagents/` 에 **다른 갈래 파일이 여럿 동시에 자라고 있었다** (이번에 17개).
  「가장 최근에 바뀐 파일」로 자기 파일을 고르면 틀린다 — 실제로 한 번 틀렸다.

### 명령 꼴

```
effort mark start "<이름>"          # 시각을 찍고 mark id 를 알려 준다
effort mark stop  [<mark id|이름>]  # 끝 시각을 찍고 잰 값을 바로 찍는다
effort mark show  [<mark id|이름>]  # 안 닫힌 mark 는 지금까지 값 (= live)
effort mark list  [--since D]       # 찍은 mark 목록
```

- **시각·길이를 받는 옵션은 없다** (`--at`·`--min` 같은 것을 안 만든다). 시각은 exe 가 부를 때의 시계다.
- 이름을 빼면 **이 transcript 에 묶인 안 닫힌 mark 하나**를 고른다. 둘 이상이면 사용법 오류로 목록을 보여 준다.

### 자기 파일 찾기 (묶기)

`mark start` 가 부를 때 한다.

1. 지금 폴더의 프로젝트 폴더(`~/.claude/projects/<slug>/`) 아래 `*.jsonl` 과 `*/subagents/agent-*.jsonl` 중
   **최근 2분 안에 바뀐 파일**만 본다.
2. 그 파일의 **끝쪽**(마지막 256KB)에서 tool_use 줄 중 입력에 `mark start` 와 **그 이름**이 함께 든 줄을 찾는다.
   본문은 저장하지 않는다 — 찾은 파일 이름과 줄의 `timestamp` 만 쓴다 (개인정보 원칙 그대로).
3. 딱 하나면 묶는다. 없으면 `묶기없음`, 둘 이상이면 `묶기모호` 를 달고 **mark 는 찍되 기록 구간은 비운다.**
4. 프로젝트 폴더에서 못 찾으면 `--all` 처럼 전 프로젝트에서 한 번 더 본다 (worktree 로 cwd 가 다를 때).

그래서 **이름은 판마다 달라야 한다.** 같은 세션에서 같은 이름 두 갈래가 동시에 시작하면 `묶기모호` 가 된다 —
스킬에 「이름에 소단계 번호를 넣는다」(예 `2-타일그림`)를 적는다.

### 잰 값

| 값 | 어떻게 | 어디에 쓰나 |
| --- | --- | --- |
| **기록 구간** | 묶인 파일의 **본줄**(`isMainLine`) 중 start~stop 사이 줄의 첫~끝 시각 | **「실제」 칸.** 기록에서 나온 값이라 원칙에 맞다 |
| 찍은 구간 | stop − start (exe 시계) | 참고·검산. 기록 구간과 20% 넘게 다르면 `어긋남` 표시 |
| 대기 | 3판. 기록 구간 안의 긴 도구 틈 합 | 어긋난 까닭 설명 |

- 기록 구간은 **서브 구간 한 판**과 같은 뜻이다. 09-23 결정대로 `estimate`·`actual` 이 `total`(본줄 ∪ 서브)이라
  **예상 칸과 같은 잣대로 견줄 수 있다.** 기록 구간이 `sub max` 를 넘으면 `상한넘음` 을 단다(자르지는 않는다 — 한 판의 실제 값이므로).
- `show`·`stats`·`list` 총계(본줄만, 09-04 결정)는 **안 바뀐다.** mark 는 그 옆의 따로 된 값이다.
- 안 닫힌 mark : `mark show` 는 「지금까지」로 찍고 `진행중` 을 단다. 묶인 파일이 끝났는데 stop 이 없으면
  그 파일의 마지막 본줄을 끝으로 보고 `끝자동` 을 단다 (stop 을 잊은 갈래를 살린다).

### 데이터 꼴 : `~/.effort/marks.txt`

- `rules.txt`·`groups.txt` 와 나란한 **세 번째 정본**이다. 다시 만들 수 없는 값이라 `--rebuild` 로 안 지운다.
- **exe 만 덧붙인다**(`store/lock.go` 의 락 그대로). 고쳐 쓰지 않고 줄을 더하기만 한다.
- 탭으로 나눈다. 시각은 UTC RFC3339(ms). 줄 머리 낱말로 종류를 가른다 — 모르는 머리는 R1 처럼 건너뛴다.

```
# effort marks — effort mark 가 덧붙인다. 손으로 고치지 않는다.
start	m0923-7f3a	2026-09-23T07:31:02.123Z	<프로젝트slug>	<세션id>/agent-a45981e1	2-타일그림
stop	m0923-7f3a	2026-09-23T07:44:10.456Z
```

- mark id = `m` + 월일 + 무작위 16진 4자. 묶기 실패면 다섯째 칸이 `-` 다.
- 사람이 파일을 고쳐 시각을 바꿀 수는 있다. 캐시·groups.txt 와 같은 처지다 — **명령으로 적는 길이 없다**는 것이 원칙이고,
  파일 위조까지 막지는 않는다. 대신 기록 구간은 transcript 에서 다시 재므로 `stop` 시각을 늘려도 본줄이 없으면 값이 안 는다.

### 기존 원칙과의 관계

| 원칙 | mark 에서 |
| --- | --- |
| 시간을 손으로 적어 넣는 길은 없다 | 지킨다. 받는 것은 **이름뿐**. 시각은 exe 시계, 값은 transcript |
| 원본 JSONL 은 열기 전용 | 지킨다. 끝쪽을 읽기만 한다 |
| 쓰기는 `scan`·`group` 뿐 | **`mark start/stop` 이 셋째 쓰기 명령**이 된다 (`marks.txt` 만). README 표를 고친다 |
| 벽시계 = 본줄만 (09-04) | 총계는 그대로. 기록 구간은 따로 된 값 |
| estimate·actual 은 total (09-23) | 기록 구간이 서브 한 판 = total 의 서브 몫과 같은 잣대 |
| transcript 본문 저장 안 함 | 지킨다. 찾을 때 메모리에서만 보고 파일 이름·시각만 남긴다 |

## 3. 「대기」 표시

### 원문

- 타일작업 피드백 막힌 것 4 : 그림 생성 한 번이 8분인데 값이 「1분 미만」뿐. 「대기」 분류를 바람.
- 재료아이콘 피드백 : 요청 뒤 약 7분 기다리는 구간이 「일한 시간」과 안 나뉘어 예상 40분 ↔ 실제 11분을 설명 못 함.

### 왜 분류가 아닌가

- 분류는 **작업 한 건에 하나**다. 기다림은 한 작업 **안의 한 구간**이라 칸이 안 맞는다.
- 분류를 더하면 순위 표·시드·크기 배율을 다 다시 잡아야 하고, 옛 exe 가 `seed	대기` 에서 걸린다(R2 로 막히긴 한다).
- 「1분 미만」의 상당 부분은 **서브 구간이 총계 밖**이었던 탓이다. 09-23 에 `estimate`·`actual` 이 `total` 이 되면서 일부 풀렸다.

### 꼴

- **대기 = 도구 한 번의 tool_use → tool_result 틈 중 `wait min` 분(기본 3) 넘는 것의 합.**
  `Bash`·`PowerShell`·`Monitor`·MCP 의 기다리기 도구 모두 같게 본다 (도구 이름으로 가르지 않는다 — 새 도구에 안 깨진다).
- `show` 벽시계 줄에 `대기 8분` 칸, `mark show` 에 같은 칸. `list --group` 에 열 하나.
- **총계·표본에서 빼지 않는다.** 기다림도 그 일에 든 시간이다. 보여 주기만 한다 — 어긋남을 설명하는 칸이다.
- `wait	min	3` 은 `rules.txt` 새 종류다. R5 에 맞다(없으면 기본 3). **1판이 깔린 뒤에만** 넣는다.
